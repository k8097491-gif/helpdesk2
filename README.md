# Helpdesk — сервис IT-поддержки вуза

Реализация системы из документа «Практическая работа 7» (Python, только стандартная библиотека, хранилище — SQLite; проверено на Python 3.13, рассчитано на 3.10+).

```bash
python3 demo.py                                # полный путь заявки: от создания до оценки
python3 -m unittest discover -s tests -v       # 52 теста правил из документа
```

## Как документ отображается на код

| Раздел документа | Где в коде |
|---|---|
| Участники и роли | `enums.Role`, права — `accounts.py` (`require`, `can_view`) |
| Канал приема обращений | `intake.py` — создание заявки, вложения, «мои заявки» |
| Реестр и рабочий процесс | `workflow.py` + `store.py` (единственная точка смены статуса) |
| Классификация и маршрутизация | `routing.py`, матрица приоритетов — `rules.py` |
| Сроки и эскалация | `sla.py` — нормативы, предупреждения, эскалация |
| Уведомления и база знаний | `notifications.py`, `knowledge.py` |
| Обратная связь и аналитика | `feedback.py`, `analytics.py` |
| Администратор | `admin.py` — категории, маршрутизация, роли, нормативы |
| Университетский каталог | `directory.py`, `HelpdeskSystem.sign_in()` |
| Модель данных | `models.py` (классы), `db.py` (таблицы и связи) |

## Жизненный цикл (`rules.TRANSITIONS`)

```
Новая → Назначена → В работе ⇄ Ожидает
                      │            │
                      ├→ Эскалирована ←┘  (→ Назначена / В работе)
                      ↓
                    Решена → Закрыта → [оценка 1..5]
                      └→ Повторно открыта → В работе …
```

Любая смена статуса идёт через `TicketStore.change_status()`: он проверяет допустимость перехода и
записывает автора, время и **причину** (без причины переход невозможен). Решить или закрыть заявку без описания
решения нельзя.

## Правила, которые реализованы

- **Приоритет** = f(влияние, срочность) по матрице 3×3; диспетчер может исправить категорию/приоритет (с причиной, в историю).
- **Маршрутизация**: категория → группа, внутри группы — специалист с наименьшей нагрузкой. Нет правила — заявка ждёт диспетчера.
- **Видимость**: заявитель — свои заявки, специалист — назначенные ему, диспетчер и руководитель — все.
- **Сроки**: по приоритету (отклик и решение). Пока заявка «Ожидает» ответа заявителя, срок решения не идёт.
  `sla.check_deadlines()` один раз предупреждает о риске (≥80% срока) и о просрочке.
- **Эскалация**: исполнитель передаёт руководителю или в другую группу, причина обязательна, прежние назначения остаются в истории.
- **Закрытие**: подтверждает заявитель; при молчании — автозакрытие через N дней (`close_expired()`, N настраивается).
- **Оценка**: 1–5 и необязательный комментарий, только заявитель, только после закрытия, один раз.
- **Уведомления**: письмо или push по выбору пользователя; отправка после успешного коммита, недоставленные можно повторить.

## Пример использования

```python
from helpdesk import HelpdeskSystem, Impact, Urgency
from helpdesk.seed import seed_demo

hd = HelpdeskSystem("helpdesk.db")          # файл БД; без аргумента — в памяти
d = seed_demo(hd)                           # демо-данные (в реальной системе — через hd.admin.*)

t = hd.intake.create_ticket(d.student.id, "Не работает Wi-Fi", "Не подключается к eduroam",
                            d.cat_network.id, Impact.MEDIUM, Urgency.HIGH)
hd.workflow.start_work(t.assignee_id, t.id)
hd.workflow.resolve(t.assignee_id, t.id, "Перезапущена точка доступа в аудитории.")
hd.workflow.confirm_resolution(d.student.id, t.id)
hd.feedback.rate(d.student.id, t.id, 5, "Спасибо!")
```

Периодические задачи (запускать по расписанию, например раз в 5–15 минут):
`hd.sla.check_deadlines()`, `hd.workflow.close_expired()`, `hd.notifier.retry_undelivered()`.

## Что подключать в реальной системе

- **Каталог вуза**: реализовать `UniversityDirectory.lookup()` для LDAP/AD и передать в `HelpdeskSystem(directory=...)`.
- **Почта и push**: реализовать `DeliveryChannel.send()` (SMTP, FCM и т. д.) и передать в `HelpdeskSystem(channels={...})`.
  По умолчанию используются заглушки `MemoryChannel`.
- **Веб/REST-слой**: все методы принимают `actor_id` и сами проверяют права, поэтому поверх них можно ставить любой интерфейс.

## Допущения (в документе не заданы)

- Сроки считаются по календарному времени, без рабочих часов.
- Повторно открыть можно только решённую (ещё не закрытую) заявку; после закрытия — новая заявка.
- Один пользователь — одна роль; администратор настраивает систему, но заявки не видит.
- Вложения хранятся в БД (до 10 МБ, расширения из белого списка `rules.ALLOWED_EXTENSIONS`).

## Веб-сайт

```bash
python3 server.py            # http://127.0.0.1:8000, база helpdesk.db (новая или незаполненная БД дополняется демо-настройками)
python3 server.py --port 8080 --db prod.db --no-seed
```

`server.py` — REST-слой (`/api/...`) поверх пакета `helpdesk`, папка `static/` — интерфейс (без сборки и зависимостей):

| Файл | Что внутри |
|---|---|
| `index.html` | каркас страницы и подключение файлов |
| `style.css` | все стили; цвета ролей меняются в начале файла |
| `helpers.js` | общие переменные, запросы к серверу, окно с формой, всплывающие сообщения |
| `tickets.js` | список заявок, карточка заявки, действия над заявкой |
| `pages.js` | новая заявка, аналитика, база знаний, уведомления, администрирование |
| `main.js` | вход, меню, переключение страниц, запуск |
Все проверки прав и бизнес-правил остаются в `helpdesk/`: сервер только передаёт `actor_id` из сессии.
Если в существующей БД ещё нет заявок и не настроены группы, категории или сотрудники поддержки, обычный запуск добавит недостающие демо-данные, сохранив существующих пользователей. `--no-seed` отключает и это автозаполнение.

- **Заявитель**: форма заявки с подсказками из базы знаний, вложения, «Мои обращения», подтверждение решения, повторное открытие, оценка.
- **Специалист**: очередь, «Взять в работу», запрос сведений, решение, эскалация (руководителю или в другую группу).
- **Диспетчер / руководитель**: заявки без исполнителя, все заявки с фильтрами, назначение, смена приоритета и категории, аналитика.
- **Администратор**: пользователи и роли, группы, категории и маршрутизация, нормативы сроков, настройки.
- Раз в минуту сервер сам выполняет `sla.check_deadlines()`, `workflow.close_expired()`, `notifier.retry_undelivered()`.

Демо-логины: `student`, `teacher`, `net1`, `net2`, `pc1`, `sw1`, `dispatcher`, `manager`, `admin`; `student2` и `teacher2` — из каталога, регистрируются как заявители при первом входе.

Важно перед боевым запуском: в системе нет паролей — вход идёт по логину через `UniversityDirectory`. Для реального вуза
подключите LDAP/AD (см. выше) и поставьте сервер за HTTPS-прокси (cookie сессии сейчас без флага `Secure`). Сессии живут в памяти процесса.

### Интерфейс

Каждая роль имеет свой цветовой акцент (заявитель — синий, специалист — зелёный, диспетчер — фиолетовый, руководитель — оранжевый, администратор — бордовый).
Списки заявок: поиск, быстрые фильтры со счётчиками (просроченные, ждут ответа, эскалированные, решённые), сортировка. В карточке — шкала расхода срока решения.
Есть состояния загрузки, пустых списков и ошибок (с кнопкой «Повторить»), уведомления об успешных действиях, навигация с клавиатуры и ссылка «К содержимому».
На телефоне список и карточка заявки открываются как два экрана с кнопкой «← К списку».
